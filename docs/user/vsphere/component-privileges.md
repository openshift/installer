# Candidate vSphere privilege matrix for component-scoped credentials

This is a review and human-test matrix for `platform.vsphere.credentialType: component-scoped`, **not a certified minimum role**. It is inferred from the vSphere API calls made by the installer and its vSphere consumers. The existing [shared-credential privilege guide](privileges.md) remains the reference for `global` credentials; its combined role must not simply be copied to every component account.

For **each configured vCenter**, check the privileges of the credentials actually delivered to each consumer. A privilege on one account does not satisfy a requirement for another account. Likewise, a privilege on one vSphere object does not imply a grant on another object unless the assignment propagates. All accounts require sufficient read/visibility access to discover the objects they use; test this through their actual inventory paths. `System.View` and `System.Read` are useful candidate privilege IDs, but a successful login alone does not demonstrate that inventory discovery works.

The identifiers below are vSphere privilege IDs, **not Kubernetes RBAC**. “Candidate” means the operation strongly suggests the privilege, but the exact vCenter-enforced minimum, source/destination assignment, or release-specific code path still needs a human test. “Conditional” means do not require it for installations that do not use that operation. In particular, never infer all `VirtualMachine.*` privileges from one clone or CNS call.

## Scope source and conventions

The **Scope (vSphere object)** column records the vSphere object on which the privilege must be granted. The object names and the privilege-to-scope assignments come from the OpenShift Container Platform 5.0 installation documentation, “vCenter requirements”:

- [Roles and privileges required for installation in vSphere API](https://docs.redhat.com/en/documentation/openshift_container_platform/5.0/html/installing_on_vmware_vsphere/installer-provisioned-infrastructure#installation-vsphere-installer-infra-minimum-requirements_ipi-vsphere-installation-reqs) (Table 2.6, with the GUI equivalents in Table 2.7)
- [Minimum permissions on installer-provisioned infrastructure](https://docs.redhat.com/en/documentation/openshift_container_platform/5.0/html/installing_on_vmware_vsphere/installer-provisioned-infrastructure#installation-vsphere-minimum-permissions-ipi_ipi-vsphere-installation-reqs) (Table 2.9)
- [Minimum permissions for postinstallation management of components](https://docs.redhat.com/en/documentation/openshift_container_platform/5.0/html/installing_on_vmware_vsphere/installer-provisioned-infrastructure#post-installation-vsphere-minimum-permissions_ipi-vsphere-installation-reqs) (Table 2.10)
- [Minimum permissions for the storage components](https://docs.redhat.com/en/documentation/openshift_container_platform/5.0/html/installing_on_vmware_vsphere/installer-provisioned-infrastructure#installation-vsphere-minimum-permissions-storage_ipi-vsphere-installation-reqs) (Table 2.11)
- [Minimum permissions for the Machine API](https://docs.redhat.com/en/documentation/openshift_container_platform/5.0/html/installing_on_vmware_vsphere/installer-provisioned-infrastructure#post-installation-vsphere-minimum-machine-api_ipi-vsphere-installation-reqs) (Table 2.12)

Propagation follows “Required permissions and propagation settings” (Table 2.8) in the same section: permissions on vSphere vCenter, vSphere Datastore, vSphere Port Group, and vSphere Switch do not propagate; permission on the vSphere vCenter data center propagates when the installation program creates the virtual machine folder; and permissions on the vSphere vCenter Cluster, an existing vSphere vCenter Resource Pool, and an existing Virtual Machine Folder propagate to their children. Where a cell says “propagated”, the privilege must be assigned with that propagation setting to cover the child objects the component uses.

Two limits apply to this comparison. First, 5.0 does not publish per-component privilege scopes: Table 2.11 (storage) and Table 2.12 (Machine API) are the closest published scopes for the `storage` and machine-management accounts, and the Cloud Controller Manager and Problem Detector have no published privilege table at all. Second, several privileges in this matrix are not in any 5.0 table. Those rows are marked **not listed in 5.0**; their scope is inferred from the privilege's vSphere namespace (for example, `Host.Inventory.EditCluster` is a cluster-object privilege) and still requires the human test described below.

vSphere tags and tag categories are vCenter-wide objects, so their management privileges are granted at **vSphere vCenter**. Attaching or detaching a tag on an inventory object is a separate privilege, `InventoryService.Tagging.ObjectAttachable`, granted on that object; 5.0 lists it on vSphere Datastore, Virtual Machine Folder, and vSphere vCenter data center.

5.0 also lists `Sessions.ValidateSession` at **vSphere vCenter** for every role. It is not repeated in each component table because any account that authenticates to the vCenter needs it, but a grant of `Sessions.ValidateSession` alone proves only that the session is valid — it does not prove inventory discovery, which is why each table has explicit read-visibility rows.

## Installer (`installer`)

This is a proposed fifth component account that covers only the `openshift-install` process: install-config validation and inventory discovery, folder/tag/template scaffolding, the embedded Cluster API provider that provisions the bootstrap, control plane, and compute VMs during `create cluster`, and `destroy cluster`. Post-install Machine API and CAPV operations, CSI, the CCM, and the Problem Detector keep their own accounts. Rows marked **destroy** are needed only by `openshift-install destroy cluster`; rows marked **conditional** only when the operation applies.

The installer currently selects `machineManagement` for all of these operations (`CredentialsForVCenter`). Adopting this role means pointing the installer-side clients and the CAPV identity Secret at the installer credential instead, so the `machineManagement` account can be reduced to its post-install duties.

NSX-T routes or load balancers, if configured, have separate NSX permissions; they are not additional vSphere privilege IDs in this matrix.

## vSphere Problem Detector (`vsphereProblemDetector`)

This section covers what the detector **uses to run diagnostics**. Its current `CheckAccountPermissions` instead checks the **detector's own session** against machine-installation privilege groups; those are *observations the detector attempts to make*, not proof that it needs VM-create or tag-write privileges to perform its diagnostics. A restricted detector account will produce misleading missing-machine-privilege reports until those checks are separated or redirected to the machine-management identity. 5.0 does not publish a Problem Detector privilege table, so the scopes below are inferred. [Session setup](https://github.com/openshift/vsphere-problem-detector/blob/14a2d33817c1ddd1d753cc76decea059376e30c9/pkg/operator/vsphere_check.go#L62-L86); [account check](https://github.com/openshift/vsphere-problem-detector/blob/14a2d33817c1ddd1d753cc76decea059376e30c9/pkg/check/permissions.go#L190-L239).

| --- | --- | --- |
| vSphere vCenter (ReadOnly, propagated to children) and the node VMs' inventory ancestors, hosts, datacenters, and datastores | Read visibility (`System.View`/`System.Read` candidates) | Find VMs by provider-ID UUID; read VM, ESXi, datastore, cluster, and task properties. [Node properties](https://github.com/openshift/vsphere-problem-detector/blob/14a2d33817c1ddd1d753cc76decea059376e30c9/pkg/check/interface.go#L35-L48); [lookup](https://github.com/openshift/vsphere-problem-detector/blob/14a2d33817c1ddd1d753cc76decea059376e30c9/pkg/operator/vsphere_check.go#L334-L372). |

## Review and human-test checklist

- Use **different accounts** for each component on each vCenter: machine management, storage, Cloud Controller Manager, Problem Detector, and the proposed installer account. Test wrong-password and wrong-scope cases as well as missing privilege IDs; do not log credentials or include them in error text.
- Check the identities *delivered* to CAPV, Machine API, CSI driver/operator, CCM, and Problem Detector. CAPV has its own `identityRef` Secret in addition to the five component Secrets in `pkg/asset/manifests/openshift.go`.
- Check each configured failure domain's actual template, VM folder or parent, resource pool (including default/root pool), compute cluster, network, datastore, and vCenter root. Cover multiple vCenters, inherited versus non-propagating roles, and unreadable objects; distinguish “not found” from “not visible.”
- Verify the **scope** column against the vCenter inventory, not only the privilege ID. A privilege granted at the wrong object (for example `Datastore.Browse` on the data center rather than the datastore) does not satisfy the requirement, and a grant on a parent covers a child only when propagation is enabled.
- Test optional paths separately: OVA import versus supplied template, created versus pre-existing folder, HostGroup affinity, managed versus unmanaged StorageClass, block versus vSAN file volumes, storage policy, tagging, snapshots, and destroy of cluster-owned volumes.
- Verify a restricted detector account can perform diagnostics without being required to hold machine-management write rights; fix or explicitly waive its existing self-privilege checks. Do not count successful calls made with `machineManagement` as verification of `storage`, `cloudControllerManager`, or `vsphereProblemDetector`.
- Pin the shipped versions of CAPV, Machine API, CSI driver/operator, CCM, and detector for the target release before making these candidates a hard installation gate. The links above span an installer CAPV v1.14.0 dependency and inspected upstream commits, not one verified release payload. Compare failures with vCenter API privilege requirements and record corrections in this matrix.
